## 4. Подход к тестированию



### 4.1. Уровни

1. **Ручное** — исследовательское, UI, сценарии.
2. **Автоматизированное** — API (pytest), UI (Playwright).
3. **CI/CD** — автотесты на каждый push через GitHub Actions.



### 4.2. Техники тест-дизайна

- **Классы эквивалентности:** для `limit` в `/stats/{id}/heroes` (1..100 — валид, <1 или >100 — невалид).
- **Граничные значения:** `limit` (0, 1, 100, 101), `user_id` (существующий, несуществующий, 0, отрицательный).
- **Таблица решений:** логика W-L (`radiant_win` × `player_slot` → win/loss).
- **Диаграмма состояний:** авторизация (Гость → Ожидание Steam → Авторизован → Выход).
- **Попарное тестирование:** `scope` (all/patch) × `limit` (10, 50, 100).

## 6. Критерии входа / выхода



### 6.1. Критерии входа

- [ ] Код задеплоен на прод (Actions зелёный).
- [ ] `GET /users` возвращает 200 OK.
- [ ] `GET /stats/1` возвращает 200 OK.
- [ ] БД содержит ≥1 пользователя.
- [ ] Swagger / API доступен локально.
- [ ] Тестовое окружение готово (Chrome, Postman, pytest установлены).



### 6.2. Критерии выхода

- [ ] Все тест-кейсы выполнены.
- [ ] Pass rate ≥ 90%.
- [ ] Критические и блокирующие баги закрыты.
- [ ] Открытые баги имеют Severity ≤ Major.
- [ ] Автотесты (pytest) запускаются в CI и зелёные.
- [ ] Test Report подготовлен и залит в `docs/TestReport.md`.



## 7. Риски



| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| OpenDota API недоступна | Средняя | Высокое | Mock-данные, retry |
| Steam OpenID недоступен | Низкая | Высокое | Тестовый пользователь в БД |
| Прод недоступен | Низкая | Среднее | Локальный запуск через Docker |
| Внешние CDN не отвечают | Средняя | Низкое | Не критично |
| У пользователя закрыта история матчей | Высокая | Среднее | Проверить UI: показывать «нет данных» |
| Данные в БД устарели | Средняя | Среднее | Принудительный сбор перед тестами |
